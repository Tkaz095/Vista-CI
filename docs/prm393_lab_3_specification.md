## 2. SYSTEM ARCHITECTURAL BOUNDARIES & RULES

```
  ┌──────────────┐
  │     View     │  (UI / Flutter Screens & Widgets)
  └──────┬───────┘
         │
  ┌──────▼───────┐
  │  ViewModel   │  (State Management: Provider / Riverpod)
  └──────┬───────┘
         │
  ┌──────▼───────┐
  │   Service    │  (Business Logic & Repositories)
  └──────┬───────┘
         │
  ┌──────▼───────┐
  │ Firebase SDK │  (Direct SDK Calls)
  └──────────────┘
```

### Architectural Strict Guidelines
1. **Separation of Concerns**:
   - Views **MUST NOT** call Firebase SDK directly. All SDK operations must be encapsulated within dedicated `Service` classes.
   - Business Logic & App Logic reside in the `Service` / `ViewModel` layers.
2. **Explicit State Definitions**:
   - State objects must explicitly capture 4 distinct conditions: `Loading`, `Data / Success`, `Empty`, and `Error`.
3. **Dependency Mapping & Testing**:
   - Document dependencies inside `architecture.md`.
   - Provide mock services / repositories for unit and integration testing.
4. **Environment & Secrets Safety**:
   - Use `flutterfire configure`.
   - **DO NOT** commit secrets, API keys, or private credential files to GitHub repository.

## 4. DETAILED SERVICE INTEGRATION REQUIREMENTS

### 4.1 Firebase Authentication (Auth 01)
- **Role**: Identity management and Google Sign-In persistence.
- **Implementation**:
  - Enable Google Sign-In in Firebase Console.
  - Monitor auth state using `authStateChanges` stream to reactively switch between `Login` and `Home` screens.
  - Handle Sign-Out flow (clear user-bound local state completely).
  - Android SHA fingerprint setup required.
- **Error & Edge Case Handling**:
  - User cancellation during Google Sign-In popup.
  - Network disconnection during auth attempt.
  - Unauthorized screen access blocking (Route Guards).

### 4.2 Firebase Cloud Storage (Storage 02)
- **Role**: Cloud file storage (e.g., PDF reports generated by application).
- **Implementation**:
  - Path pattern: `reports/{uid}/...`
  - Upload file, track upload progress, and obtain download URL upon completion.
  - Deploy custom `storage.rules` (Owner-only read/write access based on `request.auth.uid`).
- **Forbidden Practice**:
  - **NEVER** use open public rules (`allow read, write: if true;`).

### 4.3 Firebase Cloud Messaging - FCM (Messaging 03)
- **Role**: Push notification delivery and deep linking.
- **Implementation**:
  - Request runtime push permissions on **Android 13+** (POST_NOTIFICATIONS).
  - Save received notifications in an in-app Notification Center/History.
  - Handle 3 distinct runtime app states:
    1. **Foreground** (app open).
    2. **Background** (app minimized).
    3. **Terminated** (app completely closed).
  - Map notification tap actions to specific target screens.

### 4.4 Google Analytics for Firebase (Analytics 04)
- **Role**: User event tracking and product flow analysis.
- **Implementation**:
  - Pre-requisite document: Create `docs/analytics-plan.md` prior to coding tracking logic.
  - Implement **at least 7 distinct events** (Login/Logout, Main Action, Detail View, File Export, etc.).
  - Follow standard recommended names; custom event names must use `snake_case`.
  - Set `User ID` upon successful login.
- **Privacy Rule**:
  - **DO NOT** send Personally Identifiable Information (PII) such as raw email addresses or real names inside event parameters.

### 4.5 Firebase Crashlytics (Crashlytics 05)
- **Role**: Real-time crash reporting and non-fatal error logging.
- **Implementation**:
  - Initialize Crashlytics alongside Flutter's global error handler (`FlutterError.onError`, `PlatformDispatcher.instance.onError`).
  - Send non-fatal errors from actual error handler routines.
  - Attach current `User ID` and at least **1 custom diagnostic key/value pair**.
  - Provide a dedicated, intentional trigger button for testing crashes (strictly restricted to demo/debug zone).

### 4.6 Firebase Remote Config (Remote Config 06)
- **Role**: Dynamic application behavior modification without app re-deployment.
- **Implementation**:
  - Define **at least 2 parameter keys** and in-app fallback default values.
  - Bind parameters to observable UI/feature changes (e.g., feature toggle flag, maximum display item limit).
  - Fetch and activate values via dedicated service module.
  - Graceful degradation: Fall back to local default values on offline state or fetch failure.

- **Test Suite Requirement**: Write at least **10 test cases**.

- **Execution Criteria**:
  - Run each test case a minimum of **3 times**.

- **Coverage Requirements**:

  - Cover at least 1 native Android interaction (e.g., permissions prompt).
  - Verify actual observable UI state changes (do not rely solely on internal `SUCCESS` enum statuses).

- **Logged Findings**: Record at least **5 code-line-specific findings** spanning across at least 2 distinct categories (e.g., Performance, Security, Maintainability, MVVM adherence).
- **Resolution Log**:

  - Refactor and resolve at least **3 accepted findings** verified via Git commits.
